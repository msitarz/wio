# Scope of v0.1

v0.1 is the engine and nothing else. It ships no stages, stage presets or
rulesets of its own: a project defines them in its config, and the opinionated
workflow comes in v0.2. This document names every part of v0.1 and says what it
is for, what it delivers and how it is used. The concepts are in
[concepts](concepts.md), and terms are in the [glossary](../GLOSSARY.md).

## Overview

`wio` is one command line tool with a handful of subcommands. They share the
internal packages `wio.errors`, `wio.models`, `wio.formats`, `wio.io`,
`wio.env` and `wio.ports`, which hold the shared errors, the shared types, the
file formats, and the ports.

| Part | Kind | In one line |
| --- | --- | --- |
| `wio` command line | entry point | One entry point, one exit-code contract, deterministic output. |
| `wio config` | subcommand | Read, show and validate the project's settings. |
| `wio contracts` | subcommand | Create, list, check and show Work contracts. |
| `wio templates` | subcommand | List, show and check the templates that contracts follow. |
| `wio rules` | subcommand | Create, check and list rules, also for a given path. |
| `wio context` | subcommand | Compile what an agent session reads for a Work, an action and a stage. |
| `wio trailers` | subcommand | Write and check the records that tie commits to the stages of a Work. |
| `wio log` | subcommand | Record sessions and review results, and read them back. |
| `wio-define` skill | skill | Interview, then write and check a contract. |
| `wio.errors` | internal | The errors that packages share, which the command line reports as the user's to fix. |
| `wio.models` | internal | The types the components pass to one another. |
| `wio.formats` | internal | One implementation of the formats every command uses. |
| `wio.io` | internal | Ports and adapters for files, standard streams and git. |
| `wio.ports` | internal | The ports that two or more components consume identically. |
| `wio.env` | internal | Ports and adapters for variables, clock, randomness and directories. |
| Test support | internal | The facade, builders and drivers that tests use. |

How the packages may depend on each other, and who owns a port, is stated by
[the architecture of `src/wio`](../src/wio/README.md).

Fixed locations in v0.1, configurable later: the config is
`.agents/wio/config.toml`, and rulesets are in `.agents/wio/rules/<ruleset>/`,
each with its `ruleset.toml`. The Works directory is `[works] dir`,
`.agents/wio/works` by default
([Which files are Works](concepts.md#which-files-are-works)), and the templates
directory is `[templates] dir`, `.agents/wio/templates` by default
([Kinds and entry templates](concepts.md#kinds-and-entry-templates)).

## The `wio` command line

**Purpose.** Give people and agents one way to reach every component, and make
every command behave the same way.

**Outcome.**

- The package installs a `wio` command, and it can be run straight from the
  repository without a release.
- Every subcommand follows one contract for exit codes: success (0), a failed
  check (1), a usage mistake or an error the user must fix, a `WioError` (2),
  and a bug in wio (70) are four different codes. Notes and warnings do not
  change the exit code.
- Output is deterministic: sorted, with no timestamps. Where a tool consumes
  output, a machine-readable form is available. `wio log`, which reports when
  events happened, is the one place where times are shown.
- Commands that run often, such as `wio context`, start fast, so they load only
  what they need.

**Usage.** `wio <subcommand>`.

## `wio config`

**Purpose.** Keep every project setting in one file, and tell the user
precisely where a value comes from and whether the settings are consistent.

**Outcome.**

- The config declares:
  - the kinds, each with its entry template;
  - the actions, each with a description, the actions it comes `after`, what
    invalidates its work (`invalidated_by`, with `@descendants:` and
    `@dependencies:` for related Works), and whether it is on demand;
    - the roots, each keyed by its name, with a list of paths and the rule
    presets that select its rules;
  - the stages, each with a goal or a skill, optional roots, the rules it
    includes and excludes, whether it is a gate, and a session policy;
  - the stage presets, the rule presets and the result vocabulary;
  - `rules_always_include` and `rules_always_exclude`;
  - for a ruleset, an optional alias and whether it is root-independent;
  - extra directories to look up skills in, for skills only wio uses;
  - the trailer reader, an optional bundle size threshold, and the separator
    between rules in a bundle.

  The locations of the config and the rulesets are fixed in v0.1, and become
  settings later; the Works and templates directories are `[works] dir` and
  `[templates] dir` ([concepts](concepts.md#which-files-are-works),
  [concepts](concepts.md#kinds-and-entry-templates)).
- `wio config` shows the effective settings and the source of each value.
- `wio config` checks that every reference resolves:
  - the `[templates]` table, if present, has the right shape: `dir` is a path
    and `kinds` maps each kind to a template name. `wio config check` reads no
    template, so a project without a `[templates]` table passes it, and
    whether the templates and kinds agree is
    [`wio templates check`](#wio-templates)'s
    ([concepts](concepts.md#kinds-and-entry-templates));
  - stage presets use known stages, no stage appears twice in one pipeline,
    and stages use known roots (or `@work`);
  - every reference in a rule preset, a root, a stage or an always field
    resolves and has the form of its kind, rule presets have no cycle, and
    each field takes only the kinds it accepts
    ([concepts](concepts.md#checking-rules));
  - `after` names declared actions, none of them on demand, and has no cycle;
    `invalidated_by` names declared actions, with a known prefix if any; an
    entry that starts with any other `@` is reserved for v0.2 and gets a note;
  - a gate's `judge`, if set, is `"human"`;
  - every stage has exactly one of a goal and a skill, and its skill is found
    in the config's skill directories or in the project's `.agents/skills` or
    `.claude/skills`, never in the user's home;
    - rulesets exist with a `ruleset.toml`, aliases are unique, and no root
    reaches a root-independent ruleset;
  - root paths are normalized, stay inside the repo and are not listed twice in
    one root. A path that does not exist yet is a warning;
  - `[works] hierarchy`, if set, is `"flat"` or `"nesting"`
    ([Parent and leaf](concepts.md#parent-and-leaf)).
- It lists kinds, actions, roots, stages, stage presets, rule presets, rulesets
  and results.

**Usage.** `wio config` to show the settings, to check them, and to list the
named things in them.

## `wio contracts`

**Purpose.** Create contracts, keep them valid, and let people and agents see
a Work in its context. Templates have a command of their own,
[`wio templates`](#wio-templates), so each command covers the term of wio it
names.

**Outcome.**

- **Create.** `wio contracts new [<kind>]` creates a Work from the kind's entry
  template, and `--template <name>` from another template. It prepares the
  template as a contract skeleton: it promotes the template's `[contract]` table
  to the top level, drops the template's own keys, sets `id` and `template`, and
  removes comments from the metadata. The id is new among the Works in the
  tree. Given neither a kind nor `--template`, it writes a bare contract that
  holds only the `id` and a title
  ([concepts](concepts.md#identity-and-location)), and `new <kind>` when no
  kinds are declared is an error. Options:
  - `--parent <id>` creates the Work inside that parent's directory, found by
    id, under `nesting`, and is an error under `flat`
    ([Parent and leaf](concepts.md#parent-and-leaf)); without it, the Work
    goes in the Works directory;
  - `--slug <slug>` names the directory, or `--title <text>` gives the title
    and a slug derived from it; an existing directory of that name is an
    error;
  - `--path <path>` writes the Work at that path instead of
    `<slug>/README.md`, following the rules in
    [Identity and location](concepts.md#identity-and-location); it excludes
    `--slug`, and under `nesting` also `--parent`;
  - one of `--slug`, `--title` and `--path` is required;
  - `--title` also replaces the template's first heading, its title placeholder;
  - `--root <name>`, repeatable, fills `roots`, replacing the template's
    default, such as `["@descendants"]`.

  By default it writes `<slug>/README.md` in either hierarchy mode, and prints
  the new id and path, also in a machine-readable form. It does not fill in the
  body or change the parent: moving a parent to the parent template is the
  split procedure's job.
- **List.** `wio contracts list` lists the Works and never templates: each
  Work's id, title, path, template, roots and dependencies, and no status. The
  template is empty for a contract without one. Under `nesting` it indents each
  child below its parent, and under `flat` it is a plain list
  ([Parent and leaf](concepts.md#parent-and-leaf)). With no Works it prints an
  empty list and exits 0. Its columns and the shape of its `--json` output are
  provisional.
- **Check.** It verifies the invariants in
  [concepts](concepts.md#invariants-wio-checks):
  - for a contract that names a template, that the template exists and that
    `wio templates check` accepts it; a contract whose template is missing or
    rejected is reported with a pointer to `wio templates check`, which gives
    the findings, instead of repeating them;
  - a non-empty set of actions, and existing actions, stage presets, stages and
    roots; for a contract without a template, directives that parse, and a
    warning for a directive comment in a contract that follows a template
    ([concepts](concepts.md#directives));
  - what counts as a Work: no duplicate ids, and a readable metadata block in
    every marked file, whose marker, if any, names a known version
    ([Which files are Works](concepts.md#which-files-are-works)); under
    `nesting`, no directory with two or more marked files and no marked file
    directly in the Works directory
    ([Parent and leaf](concepts.md#parent-and-leaf));
  - existing dependency ids without cycles. An id not in the tree is looked up
    in the history: with no record it is an error, and with one it is a note
    that shows the latest record and counts the dependency as satisfied;
  - metadata keys: an unknown key is a warning that suggests a close known
    key, a wrong type is an error, reserved keys such as `tracks` and the
    project's own `[x]` table are left alone;
  - the sections that the template's directives require, matched by heading
    text. A `##` heading the template does not have is a warning, and so,
    under `nesting`, is a Work whose children do not match its template's
    `shape`;
  - the item ids of the Work's own sections: each is unique in the contract,
    matched by one section only, and free of whitespace and commas.

  It checks only wio's parts of the Markdown files. General Markdown hygiene is
  the project's own tooling.
- **Show.** `wio contracts show <id or file>` prints a Work, and in its
  resolved form it adds the inheritable sections of its ancestors. An argument
  that contains `/` or ends in `.md` is a path, and any other is an id; an id
  that no Work has is an error. It lists the Work's actions with their
  descriptions, pipelines and where each comes from
  ([concepts](concepts.md#where-the-pipeline-comes-from)), its roots (with
  `@descendants` resolved), and the Works that depend on it. Given a file that
  is not a Work, it fails and
  names why, with the reasons that
  [Which files are Works](concepts.md#which-files-are-works) lists: a path that
  does not exist or is not a file, a name that does not end in `.md`, no
  metadata block or one that does not start on the first line, `+++` front
  matter without a readable marker, a path outside the Works directory or
  under a dot-directory below it, and a path that is or runs through a symbolic
  link. Under `nesting` it adds the reasons that
  [Parent and leaf](concepts.md#parent-and-leaf) lists: a marked file beside
  another, and a marked file directly in the Works directory.
**Usage.** `wio contracts` to create, list, check and show. Contracts are
edited by people and agents. wio creates them but does not rewrite existing
ones.

## `wio templates`

**Purpose.** Let people and agents find, print and check the templates that
contracts follow, apart from the contracts themselves.

**Outcome.**

- **List.** `wio templates list` lists the templates with their name, kind,
  shape and description. With no templates it prints an empty list and exits
  0.
- **Show.** `wio templates show <name>` prints a template prepared as a
  contract skeleton, as `wio contracts new` would write it but without an id,
  and without creating a Work. With `--work <id>` it is the skeleton for that
  Work: the requested template, with the Work's id and dependencies carried
  over, and its roots or action overrides too when `--keep roots` or
  `--keep actions` asks for them. What is not carried is listed on standard
  error. A define skill uses it to show the agent the shape to rewrite a
  contract in, and the Work keeps its id. An unknown template name is an
  error, and so is a `--work` id that no Work has.
- **Check.** `wio templates check` checks the templates themselves: their keys,
  their kinds and their directives, that no two templates share a name, that
  the action, stage preset and stage names in every template's `[actions]`
  exist, and that each kind in `[templates.kinds]` names an entry template that
  exists and has that kind ([concepts](concepts.md#kinds-and-entry-templates)).
  With no templates it passes.

**Usage.** `wio templates` to list, show and check the templates. Templates are
written by the people who design a workflow, and wio never rewrites them.

## `wio rules`

**Purpose.** Make rules identifiable and valid, so they can be selected and
cited reliably.

**Outcome.**

- **Create.** wio creates a rule in a ruleset, assigning the number after the
  highest existing code in the family, never filling a gap, so codes never
  clash.
- **Check.** It verifies the rule files and the manifests: the metadata, the
  code and name, codes and names unique within their ruleset, and rule presets
  that name only the ruleset's own items, with no rule preset called `all`. The
  body is not checked, except that a Markdown heading in it is a warning. A rule
  that nothing selects, and a ruleset that nothing reaches or selects, are
  warnings. `rules_always_include` is reported as a note, because every session
  receives it ([concepts](concepts.md#checking-rules)).
- **List.** It lists the rules with their qualified code, name and summary,
  for a rule preset, a root, a stage, a Work at a stage or a file, and with
  `--explain` where each rule came from and why a rule is out
  ([concepts](concepts.md#listing-rules)).

**Usage.** `wio rules` to create, check and list.

## `wio context`

**Purpose.** Give an agent session exactly the guidance for its stage, in a form
that does not change between runs.

**Outcome.** For a Work, an action and a stage, `wio context` prints:

1. a header with the Work, the action, the stage, whether the stage is a gate,
   the session advice, the number of rules, the size of the bundle in bytes and
   lines, a short bundle id, the exact command that produced it, and for a stage
   with a skill, the directory it was found in and a hash of its files;
2. the stage's goal, or the instruction to read its skill's `SKILL.md`;
3. the resolved contract, without metadata blocks and directive comments
   ([concepts](concepts.md#what-it-is));
4. the selected rules: root-independent rules first, then grouped by the set
   of roots they apply to, each group under one line that names the roots,
   sorted by name, and their paths, the groups sorted by their root names, then
   by ruleset, family and code, each as a line with its
   qualified code and name followed by its body as written, with the
   configured separator between rules;
5. one fixed closing line that says to run the command again after the context
   is compacted.

Rules are selected in four layers, the rule presets of the roots the stage
selects, the stage's own selection, `rules_always_include` and then
`rules_always_exclude`, and a selected rule applies when its ruleset is
root-independent or reached by one of those roots
([concepts](concepts.md#how-a-rule-is-selected)). The roots are the stage's own,
with `@work` standing for the Work's roots, or the Work's roots when the stage
names none. The output is byte-for-byte the same for the same inputs. An unknown
Work, action, stage or root is an error, and so is a stage that selects the
Work's roots when the Work has none. A stage that is not in the given action's
pipeline for the Work is a warning, because the driver decides. A bundle larger
than the configured threshold is a warning. `--output` writes the bundle to
`wio/<repo>/<bundle-id>.md` in the temporary directory of `wio.env` and prints
the path, failing when that directory cannot be used, and `--output <path>`
writes it where it is told, with a warning for a path inside the worktree. For a
stage with a skill, the bundle tells the agent to read the skill's `SKILL.md`
instead of including it. It can explain why each rule was included or excluded,
and it records a `context` event.

**Usage.** The agent runs `wio context` as the first step of a stage, and again
after its context is compacted. The driver names the Work, the action and the
stage.

## `wio trailers`

**Purpose.** Let every commit of a stage carry a correct record with one
command, so agents need almost no instructions, and let a project check records
before they reach the history.

**Outcome.**

- **Write.** `wio trailers <work>[,<work>...] <action> <stage>`, with optional
  `--items`, `--result`, `--judge` and `--cite`, prints one record as a
  paragraph of `Wio-*` trailers. One id names one Work, and a comma-separated
  list names several that share the rest of the record, as when one gate
  approves a parent and its children. It checks that each Work exists in the
  working tree or in `HEAD` (a Work the commit deletes), that the item ids are
  among each listed Work's own item ids, and that the result is in the
  vocabulary and given exactly when the stage is a gate. A stage that is not in
  the given action's pipeline for a Work is a warning. `wio trailers none`
  prints the record of a commit that belongs to no Work.
- **Review.** With `--result`, it also writes the `review` event, once for each
  Work listed, with the items `--cite` names, so a gate records its result and
  its detail with one command. It always writes `Wio-Judge`: `agent` by default,
  `human` with `--judge human`, which a gate with `judge = "human"` requires.
  The reviewed commit is the newest commit before the gate's own commits, found
  by skipping back past the pure gate commits, which have at least one record,
  all belonging, with lists expanded, to this gate's action and stage;
  `--reviewed <sha>` overrides it. It warns when that commit differs from the
  one the gate session's first `context` event for the gate recorded, and when
  the review started on a tree with uncommitted changes.
- **Check.** `wio trailers check` reads a commit message or a pull request body
  with the configured reader, in one of two modes:
  - `--require`, at commit time: it checks every record as the writer does
    (the Work in the index or `HEAD`, its item ids, the config's names, a
    result exactly on gates) and fails on any problem, and on a message without
    a record, except merge, revert, reapply, fixup and squash commits. An
    `amend!` commit is checked, because its message replaces its target's. A
    project calls it from a commit-msg hook;
  - the plain check, afterwards, for bodies and ranges in CI: it checks the
    shape (including the ids of a list) and warns about names the current
    config does not know, so a record valid when written never fails later. A
    message without a record passes.

  In both, a `Wio-` line the reader cannot see is reported, as an error at
  commit time and a warning afterwards.
- The record format, the lists of Works, the folded form of a pull request body
  and the readers are described in [concepts](concepts.md#records). Reading
  progress from the history is not part of v0.1; the walk back from `HEAD` that
  finds a reviewed commit is.

**Usage.** An agent runs `wio trailers` for every commit of a stage and appends
the output to the commit message. A reviewer adds `--result` and `--cite`.

## `wio log`

**Purpose.** Keep the record of what happened in sessions that cannot be rebuilt
later, so cost and quality can be analyzed.

**Outcome.**

- An append-only log of JSON lines in the Wio home, one file per
  repository, identified by its git common directory so that worktrees share it.
  Each event is one line written in a single append. It holds ids, hashes,
  codes, times and the working directory, and no prompts, no code and no free
  text.
- Two events, written by `wio context`, `wio trailers --result` and
  `wio log review`:
  - `context`: a session entered a stage, with the Work, action, stage, bundle
    id, size, the code and file hash of each rule it received, the harness and
    the session id, and for a
    gate, the commit the review starts from (found with the same rule as the
    reviewed commit) and whether the tree had uncommitted changes;
  - `review`: a gate finished, with the Work, action, stage, the reviewed
    commit, the judge, the overall result and a result for each cited rule code
    (with its file's hash) or item id. Results come from the vocabulary in
    the config.
- Writing never blocks a command, a failure is only a warning, and it can be
  turned off. The warning names the path, and when it is the default Wio home
  it says to let the harness write to `~/.agents/wio`, by an exception in the
  harness's own configuration.
- It reads the log back to show when each stage of a Work was last entered.
- It records the harness session id when the process can see it, and falls back
  to the time window and the working directory when it cannot.

**Usage.** `wio context` writes its event itself. A gate records its review
with `wio trailers --result`, or with `wio log review`, which takes the same
list of Works, in a workflow that does not use records. `wio log` shows what was
recorded.

## The `wio-define` skill

**Purpose.** Capture intent before expensive work starts: interview the driver,
then write a contract that `wio contracts check` accepts.

**Outcome.** A contract in its final template, with its assumptions and
acceptance criteria, ready for the `review-contract` gate, which runs in a fresh
session after it and ends with the driver confirming the contract. The interview
can be long, because it goes on until the skill's stop condition; its result is
the contract's shape, not a transcript, and the draft's Intent section, used as
working space, is removed. The skill is the procedure of the `define` stage, and
it:

1. creates the Work with `wio contracts new <kind> --title <title>`, unless it
   exists, and reads the context for the `define` stage;
2. interviews the driver and captures the intent in the draft's Purpose and
   Intent;
3. decides whether the Work is a leaf or a parent, and prints that template
   with `wio templates show <name> --work <id>`;
4. rewrites the contract in that shape, asks the driver for anything still
   missing, and for a parent creates the children with `wio contracts new
   --parent`;
5. checks the result with `wio contracts check`, and records each commit with
   `wio trailers`.

The skill lives in this repository at `.agents/skills/wio-define/`, and
projects copy it, like a ruleset. It is written together with this repository's
feature templates, which it names and prints with `wio templates show`.

**Usage.** The driver starts a session and runs the skill with the intent. The
skill's first step is `wio contracts new`, because `wio context` needs a Work,
and its second is `wio context` for the define stage. It is the only skill in
v0.1, and it is built last.

## `wio.models` (internal)

**Purpose.** Give the components one set of types to pass to one another.

**Outcome.** A type is a stub in `wio.models` until the Work that first needs it
replaces the stub with a `.py` of the same annotations. The stubs declare only
the types that a port names.

## `wio.formats` (internal)

**Purpose.** Implement each file format once, so no command has its own idea of
a contract, a template, a record or the Work tree.

**Outcome.** These parts are shared by the commands above:

- reading metadata in both forms (a hidden comment or `+++`), and writing it
  with `tomlkit`; the TOML decoder is part of this package, and the writer,
  with the `tomlkit` ban outside it, belongs to the Work that adds the first
  writer ([why](../src/wio/formats/README.md#the-toml-decoder));
- preparing a template as a contract skeleton;
- reading directives from headings and checking sections against them;
- reading and writing records, with the `scan` and `git` readers;
- deterministic rendering.

The Works of `config` and `contracts` decide where finding the repository and
the config, generating ids, the Work tree and the dependency graph, and
resolving roots live.

The standard library comes first: `tomllib` to read, dataclasses with explicit
validation for the models, and no Pydantic. Python 3.15's lazy imports keep
parts that are rarely needed out of the start-up path.

## `wio.io` (internal)

**Purpose.** Let a command reach the filesystem, the standard streams and git
through ports, so it never touches them directly and a test can fake them.

**Outcome.** `wio.io` declares the ports `FileSystem`, `Stdio` and `Git`, and
owns them, unlike most other ports, which their consumer owns. It has one
adapter so far, `SystemStdio`, for the standard streams. The adapters of the
other ports arrive with the Work of the first component that consumes them.

## `wio.ports` (internal)

**Purpose.** Declare a port once when two or more components need it unchanged.

**Outcome.** `src/wio/ports.pyi` declares `Settings` and `EventSink`, which
`contracts`, `rules`, `trailers` and `context` would otherwise repeat, the
settings four times and the event sink twice. It
imports only `wio.models`, and no component owns it. A component that needs a
different view of the settings or the event log declares its own port and does
not use the shared one.

## `wio.env` (internal)

**Purpose.** Let a command read what the process knows about its surroundings
through ports, so tests can fix all of it.

**Outcome.** `wio.env` declares the ports `Environment` (variables and the
working directory), `Clock`, `Entropy` and `Directories`, and imports nothing
else from wio. A port whose behavior differs by platform has one adapter for
each supported platform, Linux and macOS. The temporary directory is the one
`$TMPDIR` names when it is set to a non-empty value, and otherwise `/tmp` on
Linux or `/private/tmp` on macOS when a small test file can be written there;
it is an error when `$TMPDIR` is unset and the system directory cannot be
written. The Wio home is the one `$WIO_HOME` names when it is set to a non-empty
absolute path, and `~/.agents/wio` otherwise; a relative `$WIO_HOME` is an
error. `Directories` finds it without creating it, so the user's home directory
is read in one adapter, and only when `$WIO_HOME` is unset.

## Test support (internal)

**Purpose.** Let every component be tested through the language of the domain
and not through paths and flags, as [the test strategy](../tests/README.md)
describes.

**Outcome.** A facade that starts from a minimal valid repository (one root, one
action, one stage, one kind with its entry template) and lets a scenario change
only what it tests, plus the builders and the drivers that reach wio in process
and through the command line. It is a deliverable of v0.1, because every
acceptance test depends on it.

## Not in v0.1

- `wio next`, and with it reading records from the history (including dropping
  the records of reverted commits) and deciding which results let a gate's next
  stage start. They come with the workflow in v0.2.
- The scope check that compares a change with the roots of its Work, which
  needs the record reader.
- Importing existing specs that carry no marker, with configurable id
  generation and a looser id format

## This repository as the first consumer

This repository uses wio to build wio. Its [config](../.agents/wio/config.toml),
[templates](../.agents/wio/templates), the
[contracts ruleset](../.agents/wio/rules/contracts) and the
[contract-upkeep ruleset](../.agents/wio/rules/contract-upkeep) are the
reference that the config, contract and rule Works are built against, before any
command can read them. The records of the early Works use the config's
vocabulary, so the history lines up with it:

| Action | Stages |
| --- | --- |
| `define` | `define`, `review-contract` |
| `deliver` (a leaf) | `architecture`, `architecture-review`, `wiring`, `wiring-review`, `implementation`, `implementation-review` |
| `deliver` (a parent) | `integration`, `system-review` |
| `amend` (on demand) | `amend`, `review-amendment` |
| `ratify` (on demand) | `ratify`, `review-ratify` |

The stages that write a contract select the `contract` root, so they get the
contracts ruleset. `define` captures the intent, chooses leaf or parent,
rewrites the contract in that template and creates the children of a parent; its
goal carries these steps until the `wio-define` skill exists and the stage names
it. `review-contract` comes after it, in a fresh session, so the gate judges the
contract in its final shape, and it ends with the driver confirming it. An
amendment runs `amend` and its own gate, `review-amendment`, and a ratify runs
`ratify` and `review-ratify`, so each kind of change to a contract is judged
with the rules for it. `deliver` lists `amend` and `define` in `invalidated_by`,
together with `@descendants:deliver`, so a parent's integration becomes stale
when a child is delivered again. The deliver stages select the Work's roots,
whose contract-upkeep ruleset tells the agent writing code to ask for an
amendment instead of working around a false assumption, and to correct a stale
diagram through `ratify`. The review stages are gates (`gate = true`): every
record of theirs carries a result, `pass`, `fail` or `unknown`. A Work may use
fewer stages through its own `[actions]`.

## Order of work

The parts depend on each other in this order:

1. The v0.1 foundation, delivered and described by
   [the architecture of `src/wio`](../src/wio/README.md): the architecture
   skeleton first, then the tach enforcement and the test
   support, which depend on it. The shared types, the formats and the adapters
   come with the components that first need them.
2. `wio.errors` and the `wio` command line, which every component needs: the
   errors it can raise, and the one entry point that reports them.
3. `wio config`.
4. `wio contracts`, which needs the config and the formats.
5. `wio trailers` and `wio trailers check`, which need the config and the
   contracts. They come early because this repository's own commit-msg hook
   calls them. `--result`, which writes the `review` event and compares with the
   gate's `context` event, comes with `wio log`.
6. `wio rules`, which needs the config.
7. `wio context`, which needs the config, the contracts and the rules.
8. `wio log`, which `wio context` writes to.
9. The `wio-define` skill, which needs `wio contracts`, `wio context` and
   `wio trailers`.

Questions that each Work settles when it is defined: the config schema, the
session policy fields, the directive grammar (including how a `pattern` that
contains a comma or `-->` is written), and the form of the rule metadata.
