# Scope of v0.1

v0.1 is the engine and nothing else. It ships no stages, presets or rulesets of
its own: a project defines them in its config, and the opinionated workflow
comes in v0.2. This document names every component of v0.1 and says what it is
for, what it delivers and how it is used. The concepts are in
[concepts](concepts.md), and terms are in the [glossary](../GLOSSARY.md).

## Overview

`wio` is one command line tool with a handful of subcommands. They share one
foundation that reads and writes the file formats.

| Component | Kind | In one line |
| --- | --- | --- |
| `wio` command line | entry point | One entry point, one exit-code contract, deterministic output. |
| `wio config` | subcommand | Read, show and validate the project's settings. |
| `wio contract` | subcommand | Create, check, show and map Work contracts and their templates. |
| `wio rule` | subcommand | Create, check and list rules, also for a given path. |
| `wio context` | subcommand | Compile what an agent session reads for a Work, an action and a stage. |
| `wio trailers` | subcommand | Write and check the records that tie commits to the stages of a Work. |
| `wio log` | subcommand | Record sessions and review results, and read them back. |
| `wio-define` skill | skill | Interview, then write and check a contract. |
| Foundation | internal | One implementation of the formats every command uses. |
| Test support | internal | The facade, builders and drivers that tests use. |

Fixed locations in v0.1, configurable later: the config is
`.agents/wio/config.toml`, templates are in `.agents/wio/templates/`, Works are
in `.agents/wio/works/<slug>/`, and rulesets are in
`.agents/wio/rules/<ruleset>/`, each with its `ruleset.toml`.

## The `wio` command line

**Purpose.** Give people and agents one way to reach every component, and make
every command behave the same way.

**Outcome.**

- The package installs a `wio` command, and it can be run straight from the
  repository without a release.
- Every subcommand follows one contract for exit codes: success, a failed check,
  and a usage or configuration error are three different codes. Notes and
  warnings do not change the exit code.
- Output is deterministic: sorted, with no timestamps. Where a tool consumes
  output, a machine-readable form is available. `wio log`, which reports when
  events happened, is the one place where times are shown.
- Commands that run often, such as `wio context`, start fast, so they load only
  what they need.

**Usage.** `wio <subcommand>`.

## `wio config`

**Purpose.** Keep every project setting in one file, and tell the user
precisely where a value comes from and whether the settings are consistent.

**Outcome.**

- The config declares:
  - the types, each with its entry template;
  - the actions, each with a description, the actions it comes `after`, and
    whether it is on demand;
  - the roots, each with a name, a list of paths and the rulesets bound to it;
  - the stages, each with a goal or a skill, tags, optional roots, whether it is
    a gate, and a session policy;
  - the presets, the tag vocabulary and the result vocabulary;
  - for a ruleset, which of its rules to use and how to override their tags;
  - extra directories to look up skills in, for skills only wio uses;
  - the trailer reader, an optional bundle size threshold, and the separator
    between rules in a bundle.

  The locations of wio's own files (the config, the templates, the Works and the
  rulesets) are fixed in v0.1, and become settings later.
- `wio config` shows the effective settings and the source of each value.
- `wio config` checks that every reference resolves:
  - each type's entry template exists and has that type, and every template
    belongs to a declared type;
  - presets use known stages, no stage appears twice in one pipeline, and
    stages use tags in the vocabulary and known roots (or `@work`);
  - `after` names declared actions and has no cycle;
  - every stage's skill is found in the config's skill directories or in the
    project or user directories harnesses read, with a note when only the
    user's directory has it;
  - rulesets exist with a `ruleset.toml`, no two rulesets bound in the repo
    claim the same family prefix, and the codes and families that a ruleset's
    table includes, excludes or overrides exist;
  - root paths are normalized, stay inside the repo and are not listed twice in
    one root. A path that does not exist yet is a warning.
- It lists types, actions, roots, stages, presets, tags and results.

**Usage.** `wio config` to show the settings, to check them, and to list the
named things in them.

## `wio contract`

**Purpose.** Turn a template into a contract, keep contracts valid, and let
people and agents see a Work in its context.

**Outcome.**

- **Create.** `wio contract new <type>` creates a Work from the type's entry
  template, and `--template <name>` from another template. It prepares the
  template as a contract skeleton: it promotes the template's `[contract]` table
  to the top level, drops the template's own keys, sets `id` and `template`, and
  removes comments from the metadata. The id is new among the Works in the
  tree. Options:
  - `--parent <id>` creates the Work inside that parent's directory, found by
    id; without it, the Work goes in the Works directory;
  - `--slug <slug>` names the directory, or `--title <text>` gives the title
    and a slug derived from it; one of the two is required, and an existing
    directory of that name is an error;
  - `--title` also replaces the template's title placeholder;
  - `--root <name>`, repeatable, fills `roots`.

  It prints the new id and path, also in a machine-readable form. It does not
  fill in the body or change the parent: moving a parent to the parent template
  is the split procedure's job.
- **List.** It lists the templates with their name, type, shape and
  description.
- **Template.** `wio contract template <name>` prints a template prepared as a
  contract skeleton, exactly as `wio contract new` would write it, without
  creating a Work. A define skill uses it to show the agent the shape to rewrite
  a contract in.
- **Check.** It verifies the invariants in
  [concepts](concepts.md#invariants-wio-checks):
  - existing templates and types, a non-empty set of actions, and existing
    actions, presets, stages and roots;
  - what counts as a Work: no duplicate ids, and no directory without a
    contract between two Works;
  - existing dependency ids without cycles. A missing id is an error that names
    the Work's dependents;
  - the sections that the template's directives require, matched by heading
    text. A `##` heading the template does not have is a warning, and so is a
    Work whose children do not match its template's `shape`.

  It checks only wio's parts of the Markdown files. General Markdown hygiene is
  the project's own tooling.
- **Show.** It prints a Work, and in its resolved form it adds the inheritable
  sections of its ancestors. It lists the Work's actions with their descriptions
  and pipelines, its roots (computed for a parent without declared roots), and
  the Works that depend on it.
- **Tree.** It prints the computed Work tree with each Work's roots and their
  paths, and its dependencies, and no status.

**Usage.** `wio contract` to create, list, check, show and map. Contracts are
edited by people and agents. wio creates them but does not rewrite existing
ones.

## `wio rule`

**Purpose.** Make rules identifiable and valid, so they can be selected and
cited reliably.

**Outcome.**

- **Create.** wio creates a rule in a ruleset, assigning the next free code in
  a family so codes never clash.
- **Check.** It verifies the rule files: the metadata, the code and name, tags
  in the vocabulary, template types that are declared, unique codes and names,
  and families whose prefixes no other ruleset in the repo claims. Tags are
  checked as effective tags, and types as effective types, after the config's
  overrides, and only for the rules the config selects. The body is not
  checked. A rule
  without tags is reported as a note, because it is always on within its roots.
  A rule whose tags no stage has is a warning, because it can never be
  selected.
- **List.** It lists the rules with their code, name and summary, and marks the
  rules that are always on. With `--path <file>`, it lists the rules for that
  file: those of every root whose paths contain it, optionally narrowed by a
  stage's tags, grouped by root.

**Usage.** `wio rule` to create, check and list.

## `wio context`

**Purpose.** Give an agent session exactly the guidance for its stage, in a form
that does not change between runs.

**Outcome.** For a Work, an action and a stage, `wio context` prints:

1. a header with the Work, the action, the stage, the session advice, the number
   of rules, the size of the bundle in bytes and lines, a short bundle id, and
   the exact command that produced it;
2. the stage's goal, or the name of its skill;
3. the resolved contract;
4. the selected rules, grouped by the set of roots they apply to, each group
   under one line that names the roots and their paths, then by the set of their
   tags in a stable order, each as a line with its code and name followed by its
   body as written, with the configured separator between rules;
5. one fixed closing line that says to run the command again after the context
   is compacted.

Rules are selected by roots, then template type, then the stage's tags (all of a
rule's tags must be among the stage's). The roots are the stage's own, with
`@work` standing for the Work's roots, or the Work's roots when the stage names
none. The output is byte-for-byte the same for the same inputs. An unknown Work,
action, stage or root is an error, and so is a stage that selects the Work's
roots when the Work has none. A stage that is not one of the Work's actions is a
warning, because the driver decides. A bundle larger than the configured
threshold is a warning, and `--output <path>` writes the bundle to a file. It
can explain why each rule was included or excluded, and it records a `context`
event.

**Usage.** The agent runs `wio context` as the first step of a stage, and again
after its context is compacted. The driver names the Work, the action and the
stage.

## `wio trailers`

**Purpose.** Let every commit of a stage carry a correct record with one
command, so agents need almost no instructions, and let a project check records
before they reach the history.

**Outcome.**

- **Write.** `wio trailers <work> <action> <stage>`, with optional
  `--criteria`, `--result` and `--cite`, prints one record as a paragraph of
  `Wio-*` trailers. It checks that the Work exists in the working tree or in
  `HEAD` (a Work the commit deletes), that the criteria exist in its contract,
  and that the result is in the vocabulary and given exactly when the stage is
  a gate. A stage that is not in the Work's actions is a warning.
  `wio trailers none` prints the record of a commit that belongs to no Work.
- **Review.** With `--result`, it also writes the `review` event, with the items
  `--cite` names and `HEAD` as the reviewed commit, so a gate records its result
  and its detail with one command. It warns on uncommitted changes, and when
  `HEAD` already carries a record of the same gate.
- **Check.** `wio trailers check` reads a commit message or a pull request body
  and checks the shape of every record in it, using the configured reader: the
  keys, the id's form, declared actions and stages, results from the vocabulary
  and a result exactly on gates. It does not check that Works and criteria
  exist. A message without a record passes. With `--require`, a message
  without a record fails, except merge, revert, fixup, squash and amend
  commits. A project calls `--require` from a commit-msg hook and the plain
  check from CI.
- The record format and the readers are described in
  [concepts](concepts.md#records). Reading records from the history is not part
  of v0.1.

**Usage.** An agent runs `wio trailers` for every commit of a stage and appends
the output to the commit message. A reviewer adds `--result` and `--cite`.

## `wio log`

**Purpose.** Keep the record of what happened in sessions that cannot be rebuilt
later, so cost and quality can be analyzed.

**Outcome.**

- An append-only log of JSON lines in the user's data directory, one file per
  repository. It holds ids, hashes and codes only, no prompts, no code and no
  free text.
- Two events, written by `wio context`, `wio trailers --result` and
  `wio log review`:
  - `context`: a session entered a stage, with the Work, action, stage, bundle
    id, size, the rules it received, the harness and the session id;
  - `review`: a gate finished, with the Work, action, stage, the reviewed
    commit, the overall result and a result for each cited rule code or
    criterion id. Results come from the vocabulary in the config.
- Writing never blocks a command, a failure is only a warning, and it can be
  turned off.
- It reads the log back to show when each stage of a Work was last entered.
- It records the harness session id when the process can see it, and falls back
  to the time window and the working directory when it cannot.

**Usage.** `wio context` writes its event itself. A gate records its review
with `wio trailers --result`, or with `wio log review` in a workflow that does
not use records. `wio log` shows what was recorded.

## The `wio-define` skill

**Purpose.** Capture intent before expensive work starts: interview the driver,
then write a contract that `wio contract check` accepts.

**Outcome.** A reviewed contract made from a template, with its assumptions and
acceptance criteria. The skill creates the Work with `wio contract new <type>`,
reads the context for its define stage, fills the contract in, checks it, and
records the stage with `wio trailers`.

The skill lives in this repository at `.agents/skills/wio-define/`, and
projects copy it, like a ruleset. It is written together with this repository's
feature templates, which it names and prints with `wio contract template`.

**Usage.** The driver starts a session and runs the skill with the intent. The
skill's first step is `wio contract new`, because `wio context` needs a Work,
and its second is `wio context` for the define stage. It is the only skill in
v0.1, and it is built last.

## Foundation (internal)

**Purpose.** Implement each file format once, so no command has its own idea of
a contract, a template, a record or the Work tree.

**Outcome.** These parts are shared by the commands above:

- finding the repository and the config, with the source of every value;
- generating ids, and looking a Work up by id;
- reading metadata in both forms (a hidden comment or `+++`), and writing it
  with `tomlkit`;
- preparing a template as a contract skeleton;
- the Work tree and the dependency graph, with cycle detection and reverse
  edges;
- resolving roots: a Work's declared roots, a parent's computed union, a
  stage's roots with `@work`, and the roots that contain a path;
- reading directives from headings and checking sections against them;
- reading and writing records, with the `scan` and `git` readers;
- deterministic rendering.

The standard library comes first: `tomllib` to read, dataclasses with explicit
validation for the models, and no Pydantic. Python 3.15's lazy imports keep
parts that are rarely needed out of the start-up path.

## Test support (internal)

**Purpose.** Let every component be tested through the language of the domain
and not through paths and flags, as [the test strategy](../tests/README.md)
describes.

**Outcome.** A facade that starts from a minimal valid repository (one root, one
action, one stage, one type with its entry template) and lets a scenario change
only what it tests, plus the builders and the drivers that reach wio in process
and through the command line. It is a deliverable of v0.1, because every
acceptance test depends on it.

## Not in v0.1

- `wio next`, and with it reading records from the history (including dropping
  the records of reverted commits) and deciding which results let a gate's next
  stage start. They come with the workflow in v0.2.
- The scope check that compares a change with the roots of its Work, which
  needs the record reader.
- Tracking criteria, flat splits, joined presets, path hints for rules inside a
  root, a reader for git notes, and the setting that rewrites the metadata form.
- Stages, presets and rulesets that ship with wio, and the skills for splitting,
  reviewing and orchestrating.
- Recipes for harness hooks, a setup wizard, status or ticket connectors, delta
  injection, per-model rules, and the evaluation harness, which lives in its own
  repository.

## This repository as the first consumer

This repository uses wio to build wio. Its [config](../.agents/wio/config.toml),
[templates](../.agents/wio/templates), the
[contracts ruleset](../.agents/wio/rules/contracts) and the
[contract-upkeep ruleset](../.agents/wio/rules/contract-upkeep) are the
reference that the config, contract and rule Works are built against, before any
command can read them. The records of the early Works use the config's
vocabulary, so the history lines up with it:

| Action | Stages |
| --- | --- |
| `define` | `define`, `split`, `review-contract` |
| `deliver` (a leaf) | `architecture`, `architecture-review`, `wiring`, `wiring-review`, `implementation`, `implementation-review` |
| `deliver` (a parent) | `integration`, `system-review` |
| `ratify` (on demand) | `ratify` |

The define stages select the `contract` root, so they get the contracts ruleset.
`define` captures the intent in the draft. `split` always runs: it decides
whether the Work is a leaf or a parent, prints that template with
`wio contract template`, rewrites the contract in its shape, and creates the
children of a parent. `review-contract` comes last, so the gate judges the
contract in its final shape, together with the split. The deliver stages select
the Work's roots, whose contract-upkeep ruleset tells the agent writing code to
ask for an amendment instead of working around a false assumption, and to
correct a stale diagram through `ratify`. The review stages are gates
(`gate = true`): every record of theirs carries a result, `pass`, `fail` or
`unknown`. A Work may use fewer stages through its own `[actions]`.

## Order of work

The components depend on each other in this order:

1. Foundation and test support, with the shared models as their own leaf.
2. `wio config`.
3. `wio contract`, which needs the config and the foundation.
4. `wio trailers`, which needs the config and the contracts. It comes early
   because this repository's own commit-msg hook calls it.
5. `wio rule`, which needs the config.
6. `wio context`, which needs the config, the contracts and the rules.
7. `wio log`, which `wio context` writes to.
8. The `wio-define` skill, which needs `wio contract`, `wio context` and
   `wio trailers`.

Questions that each Work settles when it is defined: the config schema, the
session policy fields, the directive grammar, where rulesets declare their
families, and the form of the rule metadata.
