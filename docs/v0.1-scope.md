# Scope of v0.1

v0.1 is the engine and nothing else. It ships no stages, presets or rulesets of
its own: a project defines them in its config, and the opinionated workflow
comes in v0.2. This document names every component of v0.1 and says what it is
for, what it delivers and how it is used. The concepts are in
[concepts](concepts.md), and terms are in the [glossary](../GLOSSARY.md).

## Overview

`wio` is one command line tool with a handful of subcommands. They share one
foundation that reads and writes the file formats.

| Component | Kind | In one line |
| --- | --- | --- |
| `wio` command line | entry point | One entry point, one exit-code contract, deterministic output. |
| `wio config` | subcommand | Read, show and validate the project's settings. |
| `wio contract` | subcommand | Create, check, show and map Work contracts and their templates. |
| `wio rule` | subcommand | Create, check and list rules. |
| `wio context` | subcommand | Compile what an agent session reads for a Work and a stage. |
| `wio log` | subcommand | Record sessions and review verdicts, and read them back. |
| `wio-define` skill | skill | Interview, then write and check a contract. |
| Foundation | internal | One implementation of the formats every command uses. |
| Test support | internal | The facade, builders and drivers that tests use. |

Default locations, all configurable later: the config is
`.agents/wio/config.toml`, templates are in `.agents/wio/templates/`, Works are
in `.agents/wio/works/<slug>/`, and rules are in the rulesets the config binds.

## The `wio` command line

**Purpose.** Give people and agents one way to reach every component, and make
every command behave the same way.

**Outcome.**

- The package installs a `wio` command, and it can be run straight from the
  repository without a release.
- Every subcommand follows one contract for exit codes: success, a failed check,
  and a usage or configuration error are three different codes.
- Output is deterministic: sorted, with no timestamps. Where a tool consumes
  output, a machine-readable form is available.
- Commands that run often, such as `wio context`, start fast, so they load only
  what they need.

**Usage.** `wio <subcommand>`.

## `wio config`

**Purpose.** Keep every project setting in one file, and tell the user
precisely where a value comes from and whether the settings are consistent.

**Outcome.**

- The config declares the roots (each with a name, a list of paths and the
  rulesets bound to it), the stages, the presets, the tag vocabulary, the
  template types, and where Works, templates and rulesets live.
- `wio config` shows the effective settings and the source of each value.
- `wio config` checks that every reference resolves. Tags used by stages and
  rules are in the vocabulary, presets use known stages, roots and rulesets
  exist, every template belongs to a declared type, and every declared type has
  exactly one template that declares `define`.
- It lists stages, presets, tags and types.

**Usage.** `wio config` to show the settings, to check them, and to list the
named things in them.

## `wio contract`

**Purpose.** Turn a template into a contract, keep contracts valid, and let
people and agents see a Work in its context.

**Outcome.**

- **Create.** Given a type, or a template name, wio creates a Work from the
  template. It prepares the template as a contract skeleton: it promotes the
  template's `[contract]` table to the top level, drops the template's own
  keys, sets `id` and `template`, and removes comments from the metadata.
- **List.** It lists the templates with their name, type and description.
- **Check.** It verifies the invariants in [concepts](concepts.md#5-actions):
  existing templates and types, a non-empty set of actions, existing presets and
  stages, known roots, existing dependency ids without cycles, and the sections
  that the template's directives require. It also runs the Markdown hygiene
  checks on contracts.
- **Show.** It prints a Work, and in its resolved form it adds the inheritable
  sections of its ancestors. It also shows the Works that depend on it.
- **Tree.** It prints the computed Work tree with each Work's scope and its
  dependencies, and no status.

**Usage.** `wio contract` to create, list, check, show and map. Contracts are
edited by people and agents. wio creates them but does not rewrite existing
ones.

## `wio rule`

**Purpose.** Make rules identifiable and valid, so they can be selected and
cited reliably.

**Outcome.**

- **Create.** wio creates a rule in a ruleset, assigning the next free code in
  a family so codes never clash.
- **Check.** It verifies the rule files: the metadata, the code and name, tags
  in the vocabulary, template types that are declared, unique codes and names,
  and families whose prefixes no other ruleset in the repo claims.
- **List.** It lists the rules with their code, name and summary.

**Usage.** `wio rule` to create, check and list.

## `wio context`

**Purpose.** Give an agent session exactly the guidance for its stage, in a form
that does not change between runs.

**Outcome.** For a Work and a stage, or for a root before a contract exists,
`wio context` prints:

1. a header with the Work, the action, the stage, the number of rules, the
   session advice and a short bundle id;
2. the stage's goal, or the name of its skill;
3. the resolved contract, and while a Work is being defined, the prepared
   template and the resolved view of its parents;
4. the selected rules, grouped by tag in a stable order, each with its code and
   name.

Rules are selected by root, then template type, then the stage's tags (all of a
rule's tags must be among the stage's). The output is byte-for-byte the same for
the same inputs. An unknown Work, stage or root is an error. A stage that is not
one of the Work's actions is a warning, because the driver decides. It can
explain why each rule was included or excluded, and it records a `context`
event.

**Usage.** The agent runs `wio context` as the first step of a stage. The driver
names the Work and the stage.

## `wio log`

**Purpose.** Keep the record of what happened in sessions that cannot be rebuilt
later, so cost and quality can be analyzed.

**Outcome.**

- An append-only log of JSON lines in the user's data directory, one file per
  repository. It holds ids and hashes only, no prompts and no code.
- Two events: `context` (a session entered a stage, with the rules it received)
  and `verdicts` (a review round ended, with a verdict per rule code).
- Writing never blocks a command, a failure is only a warning, and it can be
  turned off.
- It reads the log back to show when each stage of a Work was last entered.
- It finds out whether the harness session id is visible to wio, and falls back
  to the time window and the working directory if not.

**Usage.** `wio context` writes its event itself. A review skill records its
verdicts with one call, and `wio log` shows what was recorded.

## The `wio-define` skill

**Purpose.** Capture intent before expensive work starts: interview the driver,
then write a contract that `wio contract check` accepts.

**Outcome.** A reviewed contract made from a template, with its assumptions and
acceptance criteria. The skill reads the context for the `define` stage, creates
the Work with `wio contract`, fills it in and checks it.

**Usage.** The driver starts a session for the `define` stage and runs the
skill. It is the only skill in v0.1, and it is built last.

## Foundation (internal)

**Purpose.** Implement each file format once, so no command has its own idea of
a contract, a template or the Work tree.

**Outcome.** These parts are shared by the commands above:

- finding the repository and the config, with the source of every value;
- generating ids, and looking a Work up by id;
- reading metadata in both forms (a hidden comment or `+++`), and writing it
  with `tomlkit`;
- preparing a template as a contract skeleton;
- the Work tree and the dependency graph, with cycle detection and reverse
  edges;
- reading directives from headings and checking sections against them;
- deterministic rendering.

The standard library comes first: `tomllib` to read, dataclasses with explicit
validation for the models, and no Pydantic. Python 3.15's lazy imports keep
parts that are rarely needed out of the start-up path.

## Test support (internal)

**Purpose.** Let every component be tested through the language of the domain
and not through paths and flags, as [the test strategy](../tests/README.md)
describes.

**Outcome.** A facade that starts from a minimal valid repository (one root, one
stage, one template) and lets a scenario change only what it tests, plus the
builders and the drivers that reach wio in process and through the command line.
It is a deliverable of v0.1, because every acceptance test depends on it.

## Not in v0.1

- `wio next`, and with it the pull request body parser and the history scan.
  They come with the workflow in v0.2.
- Tracking criteria, flat splits, custom actions, joined presets and the setting
  that rewrites the metadata form.
- Stages, presets and rulesets that ship with wio, and the skills for splitting,
  reviewing and orchestrating.
- A setup wizard, status or ticket connectors, delta injection, per-model rules,
  and the evaluation harness, which lives in its own repository.

## Names for the Works before the config exists

Until the config can name them, the pull requests of the early Works use one
vocabulary, so the history lines up with the config later.

| Action | Stages |
| --- | --- |
| `define` | `define`, `review-contract`, and `split` when the Work is split |
| `deliver` (a leaf) | `architecture`, `architecture-review`, `wiring`, `wiring-review`, `implementation`, `implementation-review` |
| `deliver` (a parent) | `integration`, `system-review` |

A Work may use fewer stages through its own `[actions]`.

## Order of work

The components depend on each other in this order:

1. Foundation and test support, with the shared models as their own leaf.
2. `wio config`.
3. `wio contract`, which needs the config and the foundation.
4. `wio rule`, which needs the config.
5. `wio context`, which needs the config, the contracts and the rules.
6. `wio log`, which `wio context` writes to.
7. The `wio-define` skill, which needs `wio contract` and `wio context`.

Questions that each Work settles when it is defined: the config schema, the
session policy fields, the directive grammar, where rulesets declare their
families, and the form of the rule metadata.
